What Sanity is, and how your page builder works

Two ideas explain the whole system: content is structured data, and pages are lists of typed blocks. Everything else in the repo is plumbing for those two ideas.

Idea 1 — Sanity stores structure, not pages

A classic CMS (the old Drupal site) stores pages: HTML-ish blobs with layout baked in. Sanity stores documents — plain JSON records with a type — and nothing visual at all. Your ClariSea product is literally this, sitting in a hosted database called the Content Lake:

{
  "_id": "demo-product-clarisea-gen3",
  "_type": "product",
  "name": [{ "language": "en", "value": "ClariSea Gen 3" }],
  "specs": [{ "label": [...], "value": "5,000", "unit": "l/h" }],
  "image": { "asset": { "_ref": "image-abc123..." } }
}

Three consequences, and they explain most of your architecture:

  • The look lives in your code, not the CMS. That is why you could redesign v2 → v3 → dark without touching a single document.
  • One fact, many places. The spec "5,000 l/h" is stored once on product and referenced by the comparison table, the finder, and the FAQ spec table. Edit once, correct everywhere.
  • Any consumer can read it. Five languages, a future app, a print sheet — same JSON.
Where does the schema fit? The Content Lake would accept any JSON. The schema (sanity/schemaTypes/, blocks/*/schema.ts) is code that tells the Studio — the editing UI at /studio — which types exist, which fields they have, and what's required. The Studio is just a React app generated from that schema; it's a client of the database, exactly like your website is.

Idea 2 — A page is an array of typed blocks

Your page document has one field that matters: content[]. It's an array where every item is a small typed object — a block:

content: [
  { "_type": "heroBlock",        "headline": "Here comes the fleece filter…" },
  { "_type": "statStripBlock",   "stats": [ … ] },
  { "_type": "productFinderBlock", "rules": [ … ] },
  { "_type": "ctaBlock",         "primaryCta": { … } }
]

The editor's job in the Studio is composition: stack blocks, fill their fields, reorder them. The frontend's job is a single mapping — for each item, look up the React component registered for its _type and render it:

That's why a "block" in this repo is one folder with three files, and why adding one is cheap:

Two one-line registrations (blocks/schemas.ts, blocks/registry.tsx) plug the folder into the Studio, the page schema, TypeGen, the renderer, demo mode and the seed script.

The bridge between the two ideas: GROQ

The website doesn't receive documents as stored — it asks for them in the shape it wants, with GROQ. One query in sanity/lib/queries.ts does three jobs at once:

*[_type == "page" && slug.current == $slug][0]{   // 1 filter: which document
  content[]{                                       // 2 walk the block array
    ...,
    _type == "productListBlock" => {               // 3 per-type projection:
      items[]{ product->{ name, image, … } }       //   follow the reference,
    }                                              //   resolve the image asset,
  }                                                //   coalesce the language
}

The arrow -> is the important glyph: it dereferences — swaps a {_ref} pointer for the actual product fields. The result is the resolved shape, and it is the contract everything downstream shares: TypeGen turns it into TypeScript types, components are typed against it, and content/demo.ts hand-writes pages in exactly that shape so the site runs with no Sanity at all.

Say it back (retrieval)

Three questions, no notes

1 · Why did three full redesigns require zero content edits?

Structured content: the Content Lake holds typed facts; components decide presentation. Redesign = new components, same documents.

2 · An editor drags the stat strip above the video in the Studio. What changes where?

Composition lives in data: content[] is reordered; PageBuilder just maps over it in order.

3 · The comparison table shows "5,000 l/h". Where is that fact stored?

The block holds a reference; GROQ's -> resolves it at query time. Edit the product once and every block that references it updates.
